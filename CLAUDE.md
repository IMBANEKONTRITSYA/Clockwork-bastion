# Проект: Заводной Бастион (Clockwork Bastion)

## Начало сессии
- Сначала прочитай `HANDOFF.md` целиком и в `TASKS.md` только раздел «Текущая очередь». `HANDOFF-archive.md` целиком не читай — ищи `grep -n '^### '`.
- Взял задачу — запиши её в «Сейчас в работе» в `HANDOFF.md`; перед остановкой обнови его (правила там же).
- Экономия лимита: отвечай кратко (итог и важное), вывод команд ограничивай (`tail`, `head -n 50`, `grep`), механические задачи отдавай субагентам (`test-runner`, `Explore`).

## Обзор
- Что это: мобильная hybrid-casual игра для Android — игрок собирает механизм из шестерней от Сердца на сетке 7×5 и защищает Стену от волн Ржави.
- Стек: Godot 4.7.x (GDScript) + Nakama (TypeScript-модули) + PostgreSQL; проверка забегов — headless Godot.
- Игра онлайн: ВСЕ валюты, предметы и прогресс живут только на сервере.
- Рынок: Россия и СНГ. Магазины: RuStore (оплата — RuStore Pay SDK) и Google Play (бесплатная витрина БЕЗ покупок). Реклама — Yandex Mobile Ads (только rewarded). Вход — гость, VK ID, Яндекс ID, Google, почта. Сервер — в России (152-ФЗ). См. ADR-003.
- Правила механик для кода: @docs/design/core-rules.md
- Что входит в MVP, а что нет: @docs/design/mvp-scope.md
- Полный дизайн-документ (читай по нужному разделу, не целиком): `docs/plan/game-plan.md`
- Решения по архитектуре: `docs/decisions/`

## Структура репозитория
- `client/` — проект Godot. `client/sim/` — симуляция боя (без графики), `client/game/` — сцены и отображение, `client/meta/` — меню, Мастерская, герои, `client/services/` — сеть, реклама, покупки, аналитика, `client/data/` — ресурсы .tres, `client/tests/` — тесты GUT.
- `server/` — модули Nakama на TypeScript: `src/rpc/`, `src/economy/`, `src/validation/`, тесты в `server/tests/`.
- `validator/` — экспорт Godot без экрана: перепроверяет журнал забега тем же кодом `client/sim/`.
- `tools/` — симулятор баланса, импорт CSV → .tres.
- `data/balance/*.csv` — единственный источник чисел баланса.
- `docs/plans/` — планы задач; `docs/decisions/` — ADR.

## Команды (из корня)
- `make test` — все тесты (клиент + сервер)
- `make test-client` / `make test-server` — по отдельности
- `make test-one T=res://tests/sim/test_power.gd` — один тест GUT (предпочтительно при работе над одним файлом)
- `make lint` — gdlint + gdformat --check + eslint + tsc
- `make determinism` — один и тот же журнал забега в клиенте и в валидаторе даёт одинаковый результат
- `make sim RUNS=10000` — симулятор баланса, отчёт в `tools/out/`
- `make data` — пересобрать `client/data/` из `data/balance/*.csv`
- `make server-up` / `make server-down` — локальные Nakama + PostgreSQL в Docker
- `make build-rustore` / `make build-gplay` — сборки для магазинов (нужны ключи, только вручную у пользователя)

## Архитектура — главное
- Слои клиента: `sim` → `game` (только читает состояние симуляции и шлёт входы) → `meta`. `sim` НЕ зависит от сцен, нод, времени и графики.
- Бой — детерминированная симуляция: фиксированный шаг 30 тиков/с, только целые числа (фиксированная точка ×1000), случайность только через `client/sim/rng.gd` с зерном от сервера.
- Ввод игрока в бою = журнал `[tick, action, args]`. Сервер получает зерно + журнал и пересчитывает забег в `validator/`.
- Клиент НИКОГДА не меняет кошелёк, инвентарь и прогресс сам — только через RPC сервера; локально лишь кэш для отображения.
- Награды за рекламу — только по серверному подтверждению Яндекс Рекламной сети; покупки — только после проверки платежа через API RuStore.
- Флаг магазина `Store.current()` (`rustore` | `gplay`) задаётся при сборке. Весь код оплаты — только за проверкой `Store.has_payments()`.
- Ежедневные сбросы и таймеры — по серверному времени, граница суток 00:00 МСК (UTC+3).
- Числа баланса — в CSV и ресурсах, не в коде.

## Стиль кода
- GDScript: строгая типизация везде (`var x: int`, типы возврата), `class_name` для переиспользуемых классов, сигналы вместо прямых вызовов вверх по дереву.
- TypeScript: strict, без `any`; ошибки сервера — через `RpcError` с кодом.
- Имена в коде — на английском; комментарии, документы и сообщения коммитов — на русском.
- Тексты интерфейса — только через ключи локализации (`tr("KEY")`), языки ru и en.

## Workflow
- Задача сложнее одного файла — сначала план в `docs/plans/<NN>-<кратко>.md` (skill `plan-feature`), потом код.
- Логика `sim/` и `server/` — сначала тест, потом реализация (TDD).
- Новая механика игрока = обучение при первом открытии (`.claude/rules/ui-tutorial.md`).
- Коммиты — Conventional Commits на русском: `feat(sim): реверс механизма`; ветки `feature/<кратко>`, `fix/<кратко>`.
- Не добавляй механики сверх `docs/design/mvp-scope.md` без явной просьбы — новые идеи записывай в «Банк идей» плана.

## ВАЖНО / Никогда
- НИКОГДА не используй `float`, `randf()`, `randi()`, `Time`, `OS.get_ticks_*` внутри `client/sim/` (хук это проверяет).
- НИКОГДА не начисляй валюту или предметы на клиенте и не доверяй числам, пришедшим с клиента.
- Не трогай ключи подписи, `.env`, `secrets/`, сервисные аккаунты Google (хук блокирует).
- Не меняй уже применённые миграции/схемы хранилища — только новые версии.
- НИКОГДА не добавляй в сборку `gplay` покупки за деньги, цены в рублях или ссылки на оплату вне Google Play (правила Google Play).
- Не используй AdMob, Google UMP и Facebook SDK — для РФ они не подходят (ADR-003).
- Не добавляй зависимости и плагины без явной просьбы.
- Не меняй версию Godot в проекте (зафиксирована в `client/project.godot` и CI).

## Перед завершением задачи
1. `make lint` и релевантные тесты; если трогал `sim/` — ещё `make determinism`.
2. Если менял числа баланса — `make data` и коротко `make sim RUNS=1000`.
3. Обнови план в `docs/plans/` (отметь сделанное), статус этапа в `TASKS.md`, «Сейчас в работе» и журнал в `HANDOFF.md`; если решение архитектурное — добавь ADR.
4. Кратко отчитайся: что сделано, как проверено, что осталось.
